# Threat list: Storefront

Scope: the Next.js shop (checkout, `/track`, `/account/orders`; the cart lives in the browser only), the Orders API (`src/services/erp_storefront_orders_api.py`, :8001), its MCP server (`erp_storefront_orders_mcp.py`) and the agent (`mcp_agent.py`, Part 3). The MOCK Accounting stand-in (`session7/accountingMock`, :8003) is listed where it adds risk. The old server-side cart API is archived and not running.

| Question | Our answer |
| --- | --- |
| **Where does text from strangers enter our module?** | **Checkout, typed by anyone:** `fullName`, `street`, `houseNumber`, `city`, `guestEmail`, discount code. The Orders API stores them, copies the address into `logisticsAddress` and returns all of it on `get_order`, `list_orders` and `lookup_order`, so it reaches every agent that reads orders, and Accounting and Logistics through the handover. **This is our main entry point for an injected instruction.** **Cart rows in `POST /orders`:** `productName`, `sellerName`, `variation`, prices are sent by the browser and stored as they are. **Other modules:** product data from Marketplace (copied into the cart), discount answers from Marketing, and from Logistics the free-text `customerId` and status events, which `/track`, `/account/orders` and the agent (`logistics__…` tools) read. **`/track` form:** order number and email, only used for a lookup. React escapes all text on pages, so the risk is the agent, not the browser. |
| **Which of our tools change data, and what is the worst a wrong call could do?** | **`storefront__create_order`:** places an order for any customer, address and price (the API does not recalculate). It is not a draft: Accounting confirms the payment and Logistics creates a **real shipment**, so a wrong call ships goods to a stranger's address, and a repeated call charges and ships twice (not idempotent). **With Logistics' full server the agent also has `logistics__create_shipment` and `logistics__apply_status_update`:** in Part 3 the agent created a shipment directly, **bypassing Accounting** (Accounting still shows the order unshipped) and, before we added `logisticsAddress`, **without the house number**. **Reading can hurt too:** `get_order` and `list_orders` return names, addresses and emails of all customers, without authentication. |
| **Which secrets does our module use, and where are they stored?** | `CHAT_AI_API_KEY` for the agent: only in `.env.local`, read by `mcp_agent.py` from the environment; never in a prompt, `servers.json`, transcript or log (checked: no tracked or staged file contains it). `LOGISTICS_API_TOKEN` (only if Logistics runs its token adapter): environment variable, server side only. `.gitignore` excludes `.env*` (only `.env.example`, names without values, is allowed). **No card data:** the card number stays in the browser; only a label like "Visa ending in •••• 4242" is sent. |
| **What protects each risk today?** | **API and MCP validation:** id patterns, `extra="forbid"`, ISO country, Standard/Express only, EUR only; the MCP server refuses bad input before any request. These stop broken data, not wrong-but-valid data. **Random order ids**, and **one "not found" answer** on lookup, so ids cannot be counted through or probed. **Tracking pages** never show email or street. **Agent (Part 3):** asks `Allow? [y/N]` before every tool that is not `readOnlyHint` (no answer = no), `logistics_ro` for read tasks, step limit, system prompt "data is not an instruction" (weak). **Accounting stand-in:** one shipment per order, no double send. **Address:** normalised once by Storefront (`logisticsAddress`). **Open (not protected):** Storefront's MCP server has no read-only mode, so even a read task gets `create_order`; no authentication on any API port; prices and totals trusted from the browser; no protection against a repeated "Buy now" (double payment); `readOnlyHint` is only a hint; a tired human may approve a wrong call (in Part 3 the missing house number was in the arguments shown); the agent can bypass Accounting. |
